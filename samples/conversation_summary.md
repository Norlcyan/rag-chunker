# PageIndex 深度解读：一种基于推理导航的无向量 RAG 方案

## 一、PageIndex 是什么

PageIndex 是 Vectify AI 开源的一种**无向量（vectorless）RAG 系统**。核心思想是：**语义相似 ≠ 真正相关**。

传统 RAG 将文档切片后用 embedding 做向量检索，通过余弦相似度召回相关片段。但对于财报、法律文件、学术论文等长文档，真正"相关"的内容往往需要多步推理才能判断——不是离 query 语义最近的片段就能回答问题。

PageIndex 的做法：把文档构建成一棵层级树索引（类似增强版目录，含标题、摘要、页码范围），然后让 LLM **在这棵树上做推理导航**，模拟人类专家翻阅长文档的方式。

## 二、核心流程

### 索引阶段（离线）

```
PDF → 解析 → 检测目录 → 提取/构建树结构 → 验证 → 递归细化 → 生成摘要 → 保存 JSON
```

三种模式自动切换（带级联回退）：
- **Mode A**：目录含页码 → 直接提取
- **Mode B**：目录无页码 → LLM 匹配章节到物理页码
- **Mode C**：无目录 → LLM 从零生成层级结构

校验准确率低于 60% 时会自动降级到下一模式。

### 检索阶段（运行时）

采用**三层渐进式加载**，绝不一次全量塞入上下文：

```
┌─────────────────────────────────┐
│ 第1层：get_document()           │  ← 仅返回文档元信息（名称、类型、页数、一句话描述）
│         选文档                   │
└────────────┬────────────────────┘
             │
┌────────────▼────────────────────┐
│ 第2层：get_document_structure() │  ← 返回树结构，已去除正文 text 字段
│         看索引，AI 推理导航       │     仅保留 title + summary + 页码
└────────────┬────────────────────┘
             │
┌────────────▼────────────────────┐
│ 第3层：get_page_content("5-7")  │  ← 仅取具体页码的原文
│         精确取原文               │     "never fetch the whole document"
└─────────────────────────────────┘
```

## 三、与向量 RAG 的对比

| | 向量 RAG | PageIndex |
|---|---|---|
| **判断依据** | "这段话和问题长得像不像" | "这段话能不能回答这个问题" |
| **核心动作** | 搜索（单步相似度匹配） | 导航（多步推理决策） |
| **文档处理** | 固定大小 chunk | 自然章节/页码范围 |
| **基础设施** | 向量库 + embedding 模型 + 分块策略 | 仅需 LLM |
| **溯源能力** | 黑盒（为什么召回这个 chunk？） | 可追溯（明确的页码引用 + 推理路径） |
| **返回内容** | N 个碎片化 chunk | 完整连续的原文段落 |

**优势**：长文档多步推理场景精度高（FinanceBench 报告 98.7%），上下文完整不碎片化，零基础设施，领域知识可直接注入检索 prompt 无需微调。

**劣势**：依赖 LLM 推理质量，延迟和成本更高，不适用海量短文档的规模检索，对文档结构有要求。

## 四、PageIndex vs 其他检索路线

目前检索增强主要有四种技术路线：

| 路线 | 核心逻辑 | 代表 |
|---|---|---|
| **字面匹配** | 关键词精确匹配 | BM25 / TF-IDF |
| **语义相似** | 向量距离 → 长得像 | 向量 RAG |
| **推理相似** | 逻辑推理 → 能回答 | **PageIndex** |
| **关系推导** | 实体关系网络推导 | Graph RAG (微软) |
| **全量预载** | 文档直接进 KV cache | CAG |

当前生产环境的主流是**向量 + BM25 混合检索**——BM25 兜底精确词汇，向量补上语义泛化，两者加权融合。这套方案胜在确定性、规模和速度，但在需要逻辑推理判断相关性时存在天花板。

## 五、PageIndex 与 Skill 模式的同构性

PageIndex 的三层加载模型和 Agent Skill 的注册/调用模式高度一致：

| 层级 | PageIndex | Skill |
|---|---|---|
| 注册/发现 | `get_document()` → doc_description | skill description |
| 匹配 | LLM 根据描述判断文档是否相关 | LLM 根据描述判断 Skill 是否匹配 |
| 加载 | 加载该文档的 JSON 索引 | 展开 Skill 的完整 prompt |
| 执行 | 按页码取原文 | 按工具/指令执行 |

本质上都是**渐进式信息加载（progressive disclosure）**——不让 LLM 一次看到全部，而是给一个"目录"，让模型自己决策下一步加载什么。

## 六、组合增强方案

PageIndex 可以与现有的向量 + BM25 管线组合，各自发挥长项：

### 串行方案：粗筛 → 精读

```
向量 + BM25 粗筛（1000篇 → 30篇）→ PageIndex doc_description 精筛（30篇 → 3篇）
→ PageIndex 结构导航 → 精确取原文 → LLM 生成
```

向量 RAG 负责"广度"，PageIndex 负责"深度"。

### 策略化触发

- **默认**：走向量+BM25（低延迟）
- **触发条件**走 PageIndex：查询含推理特征词、向量结果置信度低、用户反馈不满意时

### 关键前提

所有文档入库时需用 PageIndex 预先建好索引。建索引成本是一次性的（入库时），检索时全部复用。

## 七、实践要点

- 使用 LiteLLM 对接多 LLM 提供商，通过环境变量配置 API endpoint
- 对 OpenAI 兼容的 API（如 DeepSeek），模型名加 `openai/` 前缀即可走兼容路由
- 支持 `.env` 文件持久化配置
- 关键参数：`max_page_num_each_node`（节点页数上限）、`max_token_num_each_node`（节点 token 上限）控制索引树粒度

---

**一句话总结：向量 RAG 是搜索引擎，PageIndex 是图书管理员。一个比谁找得快，一个比谁能理解你要什么。两者不是替代关系，而是互补关系。**
